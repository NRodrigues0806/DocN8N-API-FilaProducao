Fila de Produção · PZaaS

Serviço responsável por atuar como amortecedor (buffer) do sistema PZaaS. Recebe pedidos validados do Orquestrador, enfileira de forma segura em memória (Redis), controla a vazão de envios para o Forno e garante reenvios automáticos em caso de gargalos, prevenindo a sobrecarga da operação.

Padrões Globais

Protocolo HTTP / JSON
Autenticação Header x-api-key: Consultar chave com proprietário (Obrigatório em todas as rotas, exceto /health)
Rastreabilidade Header x-pedido-id (Obrigatório para transitar o ID único do pedido)

Endpoints

GET /webhook/v1/fila/health

Endpoint de monitoramento. Verifica a saúde do serviço realizando operações de teste (Set/Get) diretamente no banco de dados Redis para garantir que a fila está responsiva.

Respostas

200 OK - Serviço operacional.

{
  "status": "ok",
  "servico": "fila"
}

POST /webhook/v1/fila

Recebe o pedido do Orquestrador. O serviço imediatamente grava o pedido no Redis (Push) para garantir persistência e, em seguida, tenta enviá-lo ao Forno. Se o Forno rejeitar (429/503), o pedido permanece retido para reenvio assíncrono.

Headers

Content-Type: application/json
x-api-key: Consultar chave com proprietário

Request Body

{
  "pedido_id": "PZ-20260908-ABC123",
  "status": "em_fila",
  "itens": [
    { "pizza_id": "marguerita", "qtd": 1 }
  ]
}

Respostas

200 OK - Pedido recebido e enfileirado no Redis.

{
  "status": "Pedido enfileirado"
}

400 Bad Request - Falha de validação (ex: ID ausente).

401 Unauthorized - Credenciais inválidas.

POST /webhook/v1/fila/liberar

Gatilho manual ou automatizado para remover o pedido mais antigo da fila (Redis Pop). Após a remoção, o serviço comunica o Orquestrador Principal via PATCH para evoluir o status do pedido.

Headers

x-api-key: Consultar chave com proprietário

Respostas

200 OK - Pedido retirado da fila e encaminhado à orquestração.

{
  "status": "sucesso"
}

401 Unauthorized - Credenciais inválidas.

Arquitetura e Resiliência

  • Worker Assíncrono (Cron): Um motor independente em background é acionado a cada 1 minuto. Ele identifica pedidos que falharam ao entrar no Forno, puxa da fila e realiza novas tentativas. Se a recusa persistir, o pedido é devolvido ao Redis (Push), garantindo 0% de perda de dados.
  • Fallback de Orquestração: Durante a rotina de liberação, caso o Orquestrador A fique indisponível (Timeout ou 5xx), a arquitetura desvia a chamada automaticamente para o Orquestrador B mantendo o payload original.
  • Observabilidade: O serviço é 100% monitorado. Transições de sucesso, gargalos no Forno e tentativas de reenvio disparam Webhooks assíncronos (POST /v1/logs) para o microsserviço de Logger.

Exemplos Práticos de Uso

Criar um Pedido na Fila (cURL)

Exemplo de como o Orquestrador deve enviar um novo pedido validado para a Fila de Produção através do terminal.

curl -X POST https://pzaas.online/webhook/v1/fila \
  -H "Content-Type: application/json" \
  -H "x-api-key: Consultar chave com proprietário" \
  -H "x-pedido-id: PZ-20260908-ABC123" \
  -d '{
    "pedido_id": "PZ-20260908-ABC123",
    "status": "em_fila",
    "itens": [
      { "pizza_id": "marguerita", "qtd": 1 }
    ]
  }'

Verificar Saúde da API (cURL)

Exemplo de chamada para o healthcheck (sem autenticação) para garantir que os testes de leitura e escrita no Redis estão operacionais.

curl -X GET https://pzaas.online/webhook/v1/fila/health

Acionar Liberação de Pedido (cURL)

Exemplo de como puxar o próximo pedido da fila (Pop). Ideal para testar a comunicação subsequente com o Orquestrador.

curl -X POST https://pzaas.online/webhook/v1/fila/liberar \
  -H "x-api-key: Consultar chave com proprietário"
